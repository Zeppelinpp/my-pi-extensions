## Review

### Correct
- **core.ts**: Revert tree logic correctly implements the spec. `buildTreeNodes` accumulates changes from `branch` indices `< i` and lets older entries overwrite same paths, so earliest snapshot wins. `computeFilesToRevert` collects changes at indices `< t` and picks the oldest entry per path. Leaf target returns empty, oldest target returns everything, and branch-foreign changes are ignored (verified by 9 core tests).
- **storage.ts**: `snapshotFile` is binary-safe via `copyFile`, and read errors other than `ENOENT` are marked `unrestorable` rather than `created`, fixing the original data-loss bug. `MAX_CHANGES` prune keeps the newest 100, `MAX_REDO` cap keeps the newest 20, and redo invalidation on new change is implemented by clearing the redo stack inside `saveChange` before appending.
- **index.ts**: Preserves tool-call granularity (snapshot at `tool_call`, anchoring via `getLeafId()` at `tool_result`). Supports all three revert modes (`all`, `conversation`, `files`). Captures pre-revert state via `snapshotForRedo` and pushes a redo entry before mutating files, enabling undo of file reverts plus conversation navigation.
- **tests**: Cover binary roundtrip, `ENOENT` handling, prune + orphan cleanup, redo LIFO/cap/clear, and `unrestorable` passthrough. All 24 tests pass.

### Fixed
- **Critical data-loss bug: orphan cleanup deleted in-flight snapshots** (`storage.ts:saveChange`, `index.ts:tool_result`).
  - `saveChange` prune only referenced snapshot dirs; snapshot dirs created by concurrent `tool_call` handlers but not yet recorded by their `tool_result` were treated as orphans and deleted. This would break revert for those files.
  - Fix: `saveChange` now accepts an optional `protectedSnapshotIds: Set<string>` and skips those directories during orphan cleanup. `index.ts` passes all currently pending snapshot IDs when saving a change.
- **Data-loss risk in `deleteFileAndCleanDirs`** (`storage.ts`).
  - Used `rm(absPath, { recursive: true, force: true })`, which could recursively delete a directory if the tracked path had become a directory.
  - Fix: switched to `unlink` so directories are refused, and only empty parent directories are removed.
- **Prefix bug in `cleanupEmptyDirs`** (`storage.ts`).
  - `dir.startsWith(stopAt)` would incorrectly treat a sibling directory with a common prefix (e.g. `/tmp/work2` under stopAt `/tmp/work`) as a child and could delete it.
  - Fix: use `path.relative` to verify that the directory is actually under `stopAt`.
- **Undo inconsistency when `snapshotForRedo` fails per file** (`index.ts`).
  - If capturing the pre-revert state failed for a file, the file was still reverted but the redo entry marked it `unrestorable`, so undo would leave it in the reverted state.
  - Fix: files that fail `snapshotForRedo` are now also skipped during the revert and counted in `skippedCount`.

### Warnings / Notes
- **Async ordering in tool handlers**: `tool_call` and `tool_result` handlers are async; if the extension framework does not serialize `tool_result` events, the protected-snapshot fix still relies on the `pending` Map being shared. This is the best achievable without framework-level guarantees.
- **Snapshot-only leaks**: If a session shuts down with pending tool snapshots that never get a `tool_result`, those snapshot dirs remain until a later `saveChange` in the same session cleans them up. This is a leak, not data loss.
- **Type-only imports with `.js` extension**: `index.ts` imports `./core.js` and `./storage.js`, while the test files import the `.ts` files. Node type-stripping resolves this in practice, but it is inconsistent.
- **No integration tests**: The full `tool_call` → `tool_result` → `revert` → `undo` flow is not covered end-to-end. Consider adding a higher-level test that exercises the `index.ts` wiring.
- **Symlink behavior**: `copyFile` follows symlinks. If a tracked path is a symlink, the snapshot captures the target content, and revert replaces the symlink with a regular file. This is acceptable for the write/edit tool paths the extension targets but worth documenting.
- **Redo navigation after cancelled conversation**: When `ctx.navigateTree(targetId)` is cancelled in `all` mode, the code correctly stops and does not revert conversation state, but files have already been reverted. The redo entry remains, so undo can restore files. This is by design and matches the UI message.
